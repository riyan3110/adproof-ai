# AdProof AI — Repair journey product contract

Status: standing product requirement for the existing Proofroom. Do not reinterpret this as a legal patent or a claim that Meta image edits always succeed.

## Visible sequence for every creative

1. **Temuan** — show the specific observed issue, with a short and neutral label. Distinguish subjective slogans from verifiable product assertions. Never imply that the product itself is dangerous merely because proof is not supplied.
2. **Tindakan selanjutnya** — give one useful action supported by the current audit. No generic instruction to inspect a large technical dossier before the user can act.
3. **Perbaikan otomatis setelah explicit consent** — pressing the real Repair control triggers the existing text-region/local-pixel edit or bounded Muse Image request, then the existing independent Muse Spark re-audit. Keep the original and candidate. Preserve consistency locks; never invent specifications or guarantee a fix.
4. **Apa yang dilakukan dan bagaimana** — show an observed change using real local repair metadata or accurately qualified text observations. Do not report an unobserved change as fixed. Expose original/revised comparison.
5. **Hasil yang bisa dipakai** — report validated, incomplete, or failed states separately from model scores. Only verified output may pass current export safeguards. For failures, explain the affected element and offer a real follow-up action where a grounded correction plan exists. Explicitly disclose extra API usage for additional user-requested attempts.

## Writing rules

- Indonesian and English should be concise, practical and nonjudgmental.
- Prefer 1 short sentence per field; no large AI-written reports in the primary workflow.
- Keep technical evidence available in separate expandable details/ZIP.
- Never manufacture claim removal, model success, product safety certification, native HD detail, or successful export.
- Never silently spend additional model credit after a reload, imported report, unsupported evidence or an unbounded correction loop.
- Do not hardcode any fixture or brand (ARUNA, LumaDesk, etc.) as the production behavior.

## Implementation and verification

- The UI uses actual state in `public/repair-journey.js` and `public/app.js`, not mock response cards.
- Reuse one existing user-triggered Repair and its automatic Verify; a failed automatic correction may only be retried with another explicit button tap and only where `planOneCorrection` finds grounded diagnostics.
- Preserve old archives, browser recovery and the existing export lock logic.
- Enforce with source regressions and mocked Chromium end-to-end tests. Real provider fidelity remains subject to authenticated live model tests.
